# Settings panels: plugins, skills, shared blocks and project trust

## General appearance
- `components/FontSettings.tsx` offers separate interface/chat and monospace (code, tool output, terminal) font-name lists in the Fonts & layout section after Appearance, together with chat font size (which also sets the terminal's, hence its "Chat & terminal font size" label; client-platform.md) and content width; the Chat section keeps only behavior switches. Every row there has one shape: a header line (label, value, reset button in a fixed 28px column) over a full-width slider, so values and resets line up. A font row puts its name field between label and value, and its slider is the weight (100–600, step 100; `aria-valuetext` adds the weight's name). Both font rows share one grid (`subgrid`), so their name fields start at the same x whatever the labels' widths in each locale. The name field is drawn in the font it names, which is the preview; keep one short section description, no separate preview lines or per-control paragraphs. `hooks/useFontPreferences.ts` stores them only in the browser (`pi-ui-font-family`, `pi-mono-font-family`), applies changes immediately through `--font-ui` / `--font-mono`, and syncs other tabs. AppShell keeps the hook mounted so restoring a font never requires opening Settings or a chat. Empty input removes the override; the original stacks stay in `app/globals.css` as `--font-ui-default` / `--font-mono-default`.
- Font names refer to fonts on the **browser's device**, not the server; no enumeration, upload or remote download. `lib/font-preferences.ts` treats commas as separators, accepts optional enclosing quotes, quotes non-generic names as data, and always appends the default stack. Never interpolate font input into a stylesheet or accept it as executable CSS. Keep raw input whitespace while typing so multi-word names remain editable.
- Each font has a separate base weight (100–600 in steps of 100, default Regular/400; it stops at 600 because headings and labels use 600 and bold text, highlighted bold and the terminal's bold use 700, so a heavier base would outweigh them), stored as `pi-ui-font-weight` / `pi-mono-font-weight` and applied through `--font-ui-weight` / `--font-mono-weight`. Missing/invalid stored weights use 400; saving 400 removes the override. Each reset clears that font's name **and** weight in one update, not the other font or chat size/width. The UI weight is inherited by ordinary interface/chat text; code/pre, highlighted code (including its inline theme styles), source-view line numbers and diffs use the mono weight. Headings, Markdown bold/inline code inside emphasis, and other explicitly weighted labels keep their original weights; do not blanket-override them with `!important`.
- General's Sidebar section (after Transcript blocks) chooses where the desktop sidebar shows the file browser: below the sessions (default) or in a tab of its own, as two options in the send key's look (`settings-send-mode-option`), with "Phones always use tabs." under them (`aria-describedby`; `.settings-chat-options + .settings-general-description` turns a section's introduction into a note under its options). `hooks/useFilesPlacement.ts` keeps it per browser (`pi-web:sidebar-files-placement`; anything but `tab` reads as `below`) through `useSyncExternalStore`, so the server and hydration render `below` and the stored choice follows; it follows another tab through `storage` events and reads the key again when a first consumer subscribes, since nobody listened meanwhile. A blocked storage still applies the choice for the page. `SessionSidebar` reads it too and switches live, without remounting the explorer or the tree (sessions.md, the toolbar row and the two layouts); on a phone the choice is kept but the tabs show.
- General's Chat section ends with the switch for pi's own `showCacheMissNotices` (#1265), saved in the global settings.json through `/api/cache-miss-notices`, not in the browser: the notices come from the server, and the pi CLI reads the same key. Its note says a project's `.pi/settings.json` can override it. After a save the open chat remounts (`onSessionReloaded`) to show or drop them; see sessions.md, Cache and cost notices.
- General's Transcript blocks section (after Chat) holds the collapse policy: one row per block type (tool calls, subagent results, extension messages, thinking), each Expanded or Collapsed in the send key's look. `lib/collapse-policy.ts` classifies a block and holds the defaults; `hooks/useCollapsePolicy.ts` keeps one `createStoredChoice()` per type (`pi-web:collapse-policy:<type>`; anything but `expanded` or `collapsed` reads as the type's default), as `useFilesPlacement` does, so the server renders the defaults, other tabs follow and a change re-renders open blocks at once. It is a display choice of this browser, like the send key and the fonts, not pi's: the pi CLI has no such setting, so nothing goes to settings.json. Defaults keep the old starts except subagent results, which start collapsed, as the owner asked. The row for thinking replaced the switch "Expand thinking blocks by default"; its old key is not read. Which block is which, and why a toggle wins, is in [sessions.md](sessions.md), Collapse policy.
- General's Built-in tools section (before the Windows-only Shell tool) shows the seven built-ins as toggles in the send key's look, saved as the global `defaultTools` through `/api/tools/settings` (`builtinTools`); new sessions on the `configured` preset get them, an open chat is not reloaded. Its rules are in [tools.md](tools.md), `defaultTools` switches.
- ChatInput remeasures an existing draft when the interface font or weight changes. TerminalPanel subscribes in its existing lifetime effect, updates xterm's family and normal weight (its bold stays xterm's default 700, above every base weight) and refits, never restarting the terminal or its SSE stream for a font change.

## Plugins and skills
- `/api/plugins` uses pi's `SettingsManager` + `DefaultPackageManager` for global/project package add (an existing local path), remove, enable and disable; the pi fork loads no npm or git package sources, so there is no update or update check. Disabling writes empty `extensions/skills/prompts/themes` arrays to the package entry. Every POST drops the provider routes' shared runtime, since a package can add or drop a provider ([models.md](models.md), Auth and model config).
- `/api/skills` lists through `DefaultResourceLoader`, so settings paths, package skills and project `.agents/skills` appear as the runtime sees them. The loader takes `noExtensions: true` (`lib/skills-service.ts`, #1226): extensions add skills only through `resources_discover` at `session_start`, which a listing never runs, so importing them added nothing and blocked the event loop on every Skills open, skill click and slash-palette open. Skills an extension discovers never showed there, before or since. Even an empty extension load re-keys the SDK's one-cwd factory cache, so a listing for a folder other than the running sessions' still makes their next start re-import. The detail pane lazily reads a selected skill through `/api/skills/content` and renders its post-frontmatter instructions as Markdown; that route permits only an exact file path returned by the same runtime loader and caps the regular-file read at 1 MiB, rather than becoming a general Markdown-file reader. Toggling a skill edits only the `disable-model-invocation` frontmatter key of its `SKILL.md`, so user formatting survives, and `PATCH /api/skills` edits only `.md` files (its roots also hold `auth.json`, settings and project files). `/api/skills/install` shells through `npx skills add ... --agent pi`; project installs run in the selected cwd. Every `npx` child (`runNpx()`: install, update, the search fallback) gets `npxEnvironment()`, the host environment without `PORT`, `NODE_ENV`, `NEXT_*` and the `PI_WEB_PASSWORD` login secret, as project commands do (ADR 0001): the package it runs is third-party code fetched from npm.
- **Skill documents.** A local link in the instructions (`MarkdownBody`'s `onNavigateLink`) opens that file in the same Instructions field. `resolveSkillLink()` resolves it from the linking document's folder, as pi resolves a skill's relative paths; `SkillDetail` keeps a stack of the documents opened, the last one shown under one Back button and its relative path. Switching skills remounts `SkillDetail`, emptying the stack. A link or Back brings the field's top, or the `#heading`, into view once the document shows: Back lands at the previous document's top, nothing saves a scroll position. A link to the skill file itself reads it without `document`. The client refuses nothing: an absolute path or a `..` past the folder goes to the route, whose message shows under Back.
- `/api/skills/content`'s optional `document` is a path in the loaded skill's `baseDir` (pi's dirname of the skill file): relative, without `..`, `\`, `:` or NUL, `.md`/`.markdown` by name and by real path, inside the folder after symlinks (`isExistingPathWithinRoots()`), a regular file up to 1 MiB. One stat before the bounded read answers a FIFO or a directory with 400 and a larger file with 413; a missing file is 404, a link out of the folder 403, and no refusal or failed read names a path. Without `document` the route reads the loaded file exactly as before.
- **Group switches.** Each sidebar group of the Skills and Plugins panels (a skill scope, a package scope; not standalone extensions) has a `ConfigSidebarGroupSwitch` in its heading row, so the list's rows keep the heading's line. As with the Models provider switch, it is on only while every row is: a partial group reads as off beside its `n/m` count and one click completes it. A panel whose group can hold rows its switch never turns on passes its own `checked`, or the switch stays off for good. One request carries the list (`PATCH /api/skills` `filePaths`, `POST /api/plugins` `packages`) and answers per item, so a refused row does not stop the rest; what was left undone shows under the heading (`ConfigSidebarGroupStatus`). An entry already in the requested state is left alone; enabling keeps an entry's own keys such as `autoload`. `SettingsManager` never throws a failed load or write (`flush()` resolves), so the bulk plugin path reads `drainErrors()`, or an unreadable settings.json would report success. Disabling empties the four resource lists and keeps no filters, so a group switched off leaves an enabled filtered package on (the SDK reports every object entry as `filtered`) and says so; the bulk route refuses it.

## Settings on a phone
- At ≤640px Settings fills the screen and shows one level at a time (`SettingsPanel`'s `usePhoneSettingsLevel`): the list of sections, a section, then a row's detail. The plain Settings button opens on the sections (`openAtHome`); the sidebar's Models and Skills buttons open their section. Above 640px the level is always the section, so a desktop window narrowed to a phone's width keeps the section it shows (the e2e's short settings panel check at 320px relies on it). The header is three columns, Back, title, close, the sides equal so the title stays centered and is cut short in its own column; Back is named after the level above and the title is the shown level's name; over a detail that is the active row's label, reported by `ConfigSidebarItem` / `ConfigListAction` after each render (a rename shows at once), never by rows in a hidden, still-mounted section.
- A split view shows one pane through `ConfigDetailNavigationContext` (`data-pane="list" | "detail"`, the phone CSS in `app/settings.css`). A row's or add button's click opens the detail unless its handler called `preventDefault()`: Models' Add provider does, and its picker's choice calls `openDetail()` (`useConfigDetailNavigation()`). Deleting a provider or a model goes back to the list (`closeDetail()`). Outside the provider (no Settings) both panes stack as before. A section's settings row above its list (Models' enabledModels banner, Sub-agents' switch) shows on the list level only (`data-phone-level` on the section host).
- Each level entered pushes a history entry that copies `history.state` (Next's router state) and keeps the URL, so the system Back goes up one level; the panel's Back calls `history.back()` while it has entries, and closing Settings drops them (`history.go(-n)`). Desktops never push.
- A level change animates with the Web Animations API (`animatePhoneLevelChange`, from a layout effect so the new level never shows in place first): going in, the main area slides in from the right with a fading edge shadow; going back, from 30% left, fading up; the header's Back and title fade in beside it. Only the new level moves (the old one is gone at once) and `.settings-dialog-main` clips it. Nothing moves under `prefers-reduced-motion`.

## Shared blocks
- Panels are built from the shared blocks in `components/SettingsUi.tsx` (`ConfigScopeTag`, `ConfigScopeSwitch`, `ConfigSaveTarget`, `ConfigAddSourceHeading`, `ConfigAddSourcePanel`, `ConfigDetailGrid`, `ConfigFooterStatus`, `ConfigTrustNotice`), `itemsToSwitch()` in `components/settings-ui-helpers.ts`, and `lib/display-path.ts`; a new settings section reuses them instead of copying a panel. `SettingsUi.tsx` takes every word as a prop and holds no state, so it renders outside the i18n provider; panels pass `t()` strings.
- **Every add pane chooses global or project in one place:** a `ConfigSaveTarget` (scope switch aria-labelled `config.saveTo`, plus the path that choice writes to) first under the pane's title, where a detail pane shows its `ConfigScopeTag` and path. Skills and Plugins get it through `ConfigAddSourceHeading` (title, the catalog links at its right, then the save target); Sub-agents put it in the detail header in place of the tag while creating. The submit button stays where its flow needs it (Install under the source box or on each skill result, Save in the footer), with why it waits beside it, not under the save target. The path is shown whole, never cut short: it wraps after a separator (`<wbr>`), then anywhere. Sub-agents offer both scopes whatever the folder's trust: profiles are not project resources that wait for it.
- **Why a control is unavailable is visible text** — a scope switch's `disabledReason` (under the switch's whole line, so controls passed as its `children` stay level with it), the note under a detail header, a footer summary that opens its diagnostics — never only a `title` tooltip, which a touch screen cannot show.
- `ConfigTrustNotice` shows its button only when given `onTrust`. Skills and Plugins take the page's `trust` and reload after a decision but have no Trust button; adding one needs AppShell's trust dialog passed to them through `SettingsPanel`.

## Project trust
- `ProjectTrustStatus` (`lib/project-trust.ts`) carries the nearest decision (pi 1.5: a saved `false` makes even a folder that requires no trust `trusted: false`, which reaches extensions' `ctx.isProjectTrusted()` and the project-package checks of Plugins and skill installs) (`decision`, `decisionPath` as `trust.json` keys it, `inherited` when an ancestor's), so exact trust, trust through a parent, an explicit `false` and no decision are told apart, for a fresh folder (`requiresTrust: false`) too. For a folder that requires no trust a broken `trust.json` goes to `decisionError`; one that requires trust still throws. `projectTrustReloadOptions()` checks `hasTrustRequiringProjectResources()` first, so it never locks `trust.json` for a fresh folder on every session start.
- `GET /api/project-trust` answers that status; `POST` trusts the folder and rebuilds its wrappers. Refusals carry a `reason` (`RouteRefusalReason` in `lib/api-types.ts`); AppShell keeps `{ error, reason }` and `components/ProjectTrustDialog.tsx` renders `trust.reason.<code>`, showing the English `error` only as an `internal` or network failure's diagnostic. Repository text in the dialog goes through `revealHiddenCharacters()` (`lib/hidden-characters.ts`).
- **Escape stacking** (`lib/stacked-dialog.ts`). Settings closes on an Escape that reaches `document` in the bubble phase with `defaultPrevented` unset (`listenForPanelEscape()`). A dialog above it (`openStackedDialog()`) takes Escape on `document` in the **capture** phase, marks it handled and calls `stopPropagation()`, so one Escape closes only that dialog and no bubble-phase listener sees it; never gate Settings on a dialog-open flag instead. The window-level Stop shortcut (`handleGlobalEscape()`, `hooks/useKeyboardShortcuts.ts`) skips a `defaultPrevented` Escape, so closing Settings or a viewer never also stops a run. An Escape that cancels an IME composition (`isComposing`, or Safari's keyCode 229) closes nothing: the dialog stops it, Settings leaves it to the input method. The trust dialog ignores Escape while trusting, but still stops it. Where focus goes when a modal opens or closes, or its control disappears or is disabled, is documented on the module's helpers (`focusModalPanel()`, `focusIfLost()`, `focusAfterChange()`).
